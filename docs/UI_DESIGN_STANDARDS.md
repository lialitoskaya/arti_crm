# Production UI Design Standard — Arti CRM

## Статус документа

Этот документ обязателен для любой задачи, которая меняет интерфейс Arti CRM:
HTML, CSS, JavaScript-rendering, компоненты, layout, фильтры, карточки, списки,
формы, иконки, состояния, адаптивность или пользовательские сценарии.

Он применяется к новой функциональности, редизайну, локальным визуальным правкам,
рефакторингу frontend и независимому review. Отклонение допускается только когда
в задаче явно зафиксирована продуктовая причина и reviewer подтвердил её.

## Цель интерфейса

Arti CRM — внутренний рабочий инструмент для обработки большого количества чатов,
задач, вопросов и данных маркетплейсов. Приоритеты интерфейса в порядке важности:

1. корректность рабочего сценария;
2. скорость выполнения операции;
3. ясность состояния и следующего действия;
4. последовательность существующей дизайн-системы;
5. высокая, но читаемая информационная плотность;
6. доступность и предсказуемость;
7. визуальная аккуратность.

Декоративная выразительность никогда не должна ухудшать эти пункты.

## Базовый принцип

Интерфейс должен выглядеть как результат работы продуктовой команды, которая
понимает конкретный CRM-процесс, реальные данные и ограничения production-системы.
Он не должен выглядеть как универсальный SaaS-template, Dribbble-концепт,
маркетинговый лендинг или демонстрация генеративного ИИ.

## Обязательные правила

### 1. Сначала существующая система

До изменения кода необходимо изучить:

- существующую разметку и hierarchy;
- CSS variables/design tokens;
- используемые размеры, радиусы, отступы и типографику;
- существующие компоненты и их состояния;
- mobile-правила;
- текущие event handlers и источники состояния;
- реальные ограничения данных и DOM.

Новый компонент создаётся только если существующий нельзя корректно расширить.
Новый token создаётся только если существующая система не выражает нужное
семантическое значение.

### 2. Исправлять первопричину

Нельзя добавлять новый визуальный или технический слой, который маскирует ошибочную
реализацию. Требуется:

1. найти самую раннюю неправильную точку;
2. определить единый источник истины;
3. заменить или упростить ошибочный путь;
4. удалить устаревшую разметку, CSS, handler или state;
5. доказать отсутствие второго конкурирующего пути.

Запрещены цепочки `override`, `!important` как постоянное решение, параллельные
версии компонента без migration plan и классы с названиями `new`, `fixed`, `final`,
`v2`, если старый путь остаётся активным.

### 3. Один визуальный язык

В одном экране должны использоваться согласованные:

- набор иконок;
- типы кнопок;
- размеры контролов;
- радиусы;
- отступы;
- типографические уровни;
- правила hover/focus/active/disabled;
- семантика цветов.

Нельзя смешивать emoji, filled-, outline- и разнотолщинные иконки без причины.

## Anti-AI-slop: запрещённые паттерны

Следующие решения запрещены по умолчанию и требуют отдельного продуктового
обоснования:

- glassmorphism и `backdrop-filter: blur(...)`;
- неоновые свечения и glow вокруг текста/контролов;
- фиолетово-синие «AI-градиенты», mesh-градиенты и абстрактные световые пятна;
- декоративные gradient borders;
- чрезмерные тени или несколько теней на одном элементе;
- большие радиусы у всех элементов независимо от функции;
- карточки внутри карточек без реальной иерархической необходимости;
- отдельная цветная подложка для каждого небольшого смыслового блока;
- огромные pill-кнопки и pill-контролы для вторичных действий;
- крупные hero-заголовки и маркетинговые слоганы в рабочем интерфейсе;
- фиктивные метрики и декоративные графики;
- чрезмерные пустые зоны и искусственно увеличенные отступы;
- центрирование основного рабочего контента без причины;
- декоративные бейджи, которые не передают состояние;
- анимации, не объясняющие изменение состояния;
- сложные hover-эффекты ради впечатления;
- скрытие ключевых действий только через hover;
- дублирование одной информации в нескольких визуальных блоках;
- одинаковая generic dashboard-card для разных по смыслу сущностей;
- новые DOM-обёртки только ради стилей;
- псевдо-минимализм, при котором важные данные или действия становятся скрытыми.

Фраза «сделать современно» не является основанием для любого из этих решений.

## Правила компонентов

### Layout и плотность

- Рабочие списки должны быть компактными и быстро сканироваться.
- Высота строки или карточки увеличивается только при наличии дополнительной
  информации, которую действительно нужно видеть сразу.
- Не оборачивать каждый блок в самостоятельную карточку.
- Группировать через alignment, spacing и typography прежде, чем добавлять рамку,
  фон или тень.
- Основные области экрана должны сохранять стабильные размеры при загрузке, чтобы
  не создавать layout shift.

### Карточки

Карточка используется, когда сущность действительно требует отдельного
контейнера. Внутри карточки:

- один главный визуальный уровень;
- ясное название/идентификатор;
- основная информация выше вторичной;
- действия не должны конкурировать с содержанием;
- metadata не повторяется без необходимости;
- вложенная карточка допустима только для самостоятельной вложенной сущности.

### Кнопки и действия

- Primary action на экране должен быть один или явно доминировать.
- Secondary actions — спокойные и компактные.
- Edit/delete/open для карточек предпочтительно представлять единым согласованным
  набором иконок с `aria-label`, `title` и достаточной hit-area.
- Опасное действие не должно быть постоянно ярко-красным; красный акцент появляется
  в hover/focus/confirmation или при критическом состоянии.
- Иконка без рамки всё равно должна иметь доступную область нажатия не менее
  примерно 32×32 CSS px на desktop и 40×40 CSS px на touch, если layout позволяет.
- Нельзя использовать текстовую кнопку там, где компактная понятная иконка уже
  является принятым паттерном проекта.

### Иконки

- Использовать один SVG-набор и одинаковую толщину stroke.
- Не использовать emoji как production-иконки.
- Иконка должна иметь семантическую подпись для screen reader.
- Не добавлять декоративную иконку, если она не улучшает распознавание действия или
  состояния.

### Цвет

- Цвет передаёт семантику, а не украшает экран.
- Акцентный цвет используется экономно для primary action, selection и ключевого
  состояния.
- Красный — ошибка, danger или критическое состояние.
- Зелёный — подтверждённый success, а не общий декоративный акцент.
- Статусы должны различаться не только цветом.
- Контраст должен оставаться достаточным в поддерживаемых темах.

### Радиусы, рамки и тени

- Использовать существующие tokens.
- Малые controls не должны выглядеть как большие «капсулы».
- Рамка применяется для различения interactive boundary или уровня, а не для
  обводки каждого элемента.
- Тень применяется только для реального elevation: popover, modal, floating layer.
- Не использовать одновременно сильную рамку, тень, фон и glow.

### Типографика

- Иерархия строится ограниченным количеством уровней.
- Не увеличивать заголовок только ради визуального «вау».
- Metadata должна быть читаемой, но не конкурировать с основной информацией.
- Не использовать uppercase для длинных строк.
- Длинные названия, имена и тексты должны иметь предсказуемые wrap/truncate rules и
  доступ к полному значению.

### Фильтры

- Фильтры группируются по объекту и смыслу.
- Нельзя создавать несколько календарей или фильтров, управляющих одной выборкой.
- Активное состояние фильтра должно быть видно.
- Сброс должен быть понятным и не требовать перезагрузки страницы.
- Backend остаётся источником истины для бизнес-фильтрации больших выборок.
- При смене фильтра stale-response не должен перезаписывать более новый результат.

### Списки и большие данные

- Не рендерить тысячи строк одновременно.
- Использовать server-side filtering и порционную/ленивую загрузку.
- Не сохранять скрытые тяжёлые разделы в DOM без необходимости.
- Стабильно сохранять selection и scroll, когда это ожидается сценарием.
- Не создавать отдельный handler на каждую строку, если подходит делегирование.
- Empty/loading/error/end-of-list состояния должны быть явными и компактными.

### Состояния

Для изменяемого компонента проверить минимум:

- default;
- hover;
- focus-visible;
- active/selected;
- disabled;
- loading;
- empty;
- error;
- long content/overflow;
- permission-limited/read-only;
- mobile/touch.

Unread, pinned, overdue, selected и marketplace status должны различаться, но не
создавать пять конкурирующих акцентов в одной строке.

### Motion

- Анимация должна объяснять появление, перемещение или подтверждение состояния.
- Не анимировать всё подряд.
- Учитывать `prefers-reduced-motion`.
- Не задерживать рабочее действие ради декоративной анимации.

### Mobile

- Не считать hover доступным.
- Touch targets должны быть достаточными.
- Нельзя допускать горизонтальный overflow из-за длинного текста или action row.
- Критические действия и статусы не должны исчезать на узком экране.
- Ввод не должен вызывать нежелательный browser zoom.
- Проверять реальные длинные данные, а не только короткие mock-строки.

### Accessibility

- Все интерактивные элементы доступны с клавиатуры.
- Использовать semantic elements до `div` с click-handler.
- Иконки имеют `aria-label`/accessible name.
- Focus-visible не удаляется без равноценной замены.
- Состояния не кодируются только цветом.
- Dialog/popover управляют focus и закрываются предсказуемо.

## Обязательный процесс UI-задачи

### До кода

Исполнитель должен кратко зафиксировать:

1. **Пользовательская проблема:** что замедляет или путает сотрудника.
2. **Текущая первопричина:** какая разметка, логика, state или CSS создаёт проблему.
3. **Источник истины:** где должно жить состояние/правило.
4. **Переиспользование:** какие компоненты, selectors и tokens будут использованы.
5. **Удаление:** какой старый код или визуальный путь будет удалён.
6. **Scope:** какие файлы разрешено менять и что намеренно не меняется.
7. **Acceptance:** проверяемые критерии desktop/mobile и состояний.

### Во время реализации

- один вертикальный срез;
- без несвязанного polish;
- без массового форматирования;
- без копирования компонента ради локального варианта;
- без нового global mutable state;
- без дублирующих listeners;
- без CSS override-chain;
- без фиктивных данных в production UI;
- без ухудшения DOM/performance.

### После реализации

Обязательно проверить:

- desktop и mobile;
- поддерживаемые темы;
- короткий и длинный контент;
- empty/loading/error/disabled;
- keyboard и focus-visible;
- screen-reader names для controls;
- permissions/read-only;
- stale requests и повторные действия;
- DOM-size/list performance;
- отсутствие duplicate IDs;
- отсутствие новых duplicate selectors/listeners/state sources;
- отсутствие старого параллельного пути;
- before/after screenshots;
- полный substantive diff.

## Mandatory prompt для любого UI-агента

Следующий блок считается частью любой UI-задачи, даже если пользователь не повторил
его в сообщении:

> Ты работаешь над production-интерфейсом внутренней Arti CRM, а не над лендингом,
> Dribbble-концептом или универсальным AI-dashboard. Сначала изучи существующую
> дизайн-систему, компоненты, tokens, states и реальный пользовательский сценарий.
> Переиспользуй существующие решения. Найди первопричину проблемы, замени ошибочную
> реализацию и удали старый путь; не добавляй новый слой поверх старого.
>
> Не используй без функционального обоснования glassmorphism, blur, glow,
> декоративные градиенты, большие радиусы, карточки внутри карточек, огромные
> pill-кнопки, лишние подложки, маркетинговые заголовки, декоративные бейджи,
> emoji-иконки, чрезмерные отступы и анимации. Сохраняй высокую информационную
> плотность CRM, ясную иерархию и текущий визуальный язык.
>
> До кода опиши проблему, root cause, переиспользуемые компоненты, удаляемый старый
> код и acceptance criteria. После кода проверь desktop, mobile, длинный контент,
> empty/loading/error/disabled states, keyboard, accessibility, DOM/performance и
> отсутствие дублирующих CSS, handlers и sources of truth.

## Reviewer checklist

Reviewer блокирует UI-изменение, если хотя бы один пункт не обоснован:

- [ ] Решение специфично для рабочего сценария Arti CRM, а не generic SaaS UI.
- [ ] Прочитан и применён этот документ.
- [ ] Найдена и устранена первопричина.
- [ ] Старый конкурирующий путь удалён.
- [ ] Переиспользованы существующие tokens/components.
- [ ] Нет новых AI-slop паттернов.
- [ ] Нет card-within-card без необходимости.
- [ ] Нет CSS override-chain и необоснованного `!important`.
- [ ] Нет duplicate selectors, handlers, IDs и sources of state.
- [ ] Основные и вторичные действия имеют правильную иерархию.
- [ ] Проверены desktop и mobile.
- [ ] Проверены длинные данные и overflow.
- [ ] Проверены loading/empty/error/disabled/read-only.
- [ ] Проверены keyboard, focus-visible и accessible names.
- [ ] Нет заметной DOM/performance-регрессии.
- [ ] В PR есть before/after и фактические результаты проверок.

## Примеры корректной постановки

Плохо:

> Сделай современно и премиально.

Хорошо:

> Сделай компактный production-интерфейс внутренней CRM с высокой информационной
> плотностью. Сохрани существующие tokens и hierarchy. Убери визуальный шум через
> типографику, alignment и spacing, а не через новый набор карточек, градиентов,
> теней и больших скруглений.

Плохо:

> Улучши карточки.

Хорошо:

> Оставь один визуальный контейнер сущности. Удали вложенные подложки и тяжёлые
> текстовые secondary actions. Переиспользуй существующий icon-action pattern,
> сохрани доступную hit-area и проверь длинный контент на mobile.

Плохо:

> Сделай минималистично.

Хорошо:

> Удали элементы, не передающие информацию или действие, но не скрывай статус,
> ответственного, дату и основные операции. Минимализм не должен снижать скорость
> работы или информационную плотность.
